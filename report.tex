\section{Overview}

This report describes the current state of the Plant Management ontology project.
The project uses the Trefle species dataset and a small generated shop inventory.
The goal is to create an ontology-based application for plant management and shop
queries.

The current work covers the ontology, the relational database setup, the R2RML
mapping, a full generated knowledge graph for GraphDB import, OOPS ontology
verification, SHACL validation, a first manual ontology alignment, and a
KG-backed RAG CLI. The full graph was imported and smoke-tested in the local
Docker GraphDB Workbench repository \artifact{plantms}.

\section{Assignment Requirements}

The assignment has five main steps:

\begin{enumerate}
  \item Advanced ontology engineering.
  \item Knowledge graph creation through OBDA.
  \item Verification of semantic structures.
  \item Ontology alignment.
  \item A simple KG-based RAG application.
\end{enumerate}

The final submission should contain the ontology, OBDA artifacts, SHACL files
and reports, an alignment result, the RAG application, and this project report.

\section{Domain And Application Idea}

The domain is plant management for a small plant shop. The ontology should
describe plant species, taxonomy, plant parts, plant use, growth properties,
geographic distribution, and shop products.

The application should support questions such as:

\begin{itemize}
  \item Which plants belong to a given family or genus?
  \item Which plants have specific flower, fruit, or foliage properties?
  \item Which plants are edible or have edible parts?
  \item Which shop products are easy care, warm temperature plants, or low stock?
  \item Which products have been on the shelf for a long time?
\end{itemize}

\subsection{Main Modeling Choices}

The ontology uses classes for plant taxonomy, plant parts, growth descriptors,
temporal values, geographic regions, plant use, edible parts, and shop products.
The class \artifact{Plant} represents one plant species. \artifact{Family} and
\artifact{Genus} model taxonomy. \artifact{ShopProduct} represents a product
line in the shop inventory.

The ontology uses several OWL2 features:

\begin{itemize}
  \item disjoint classes and disjoint unions for controlled vocabularies;
  \item property chains for taxonomy inference;
  \item inverse object properties;
  \item functional properties for values that should be unique;
  \item qualified cardinality and existential restrictions;
  \item datatype restrictions for numeric values.
\end{itemize}

\subsection{Ontology Design Patterns}

The current ontology uses these design patterns:

\begin{itemize}
  \item Componency pattern for plant parts such as flower, foliage, fruit, and root.
  \item N-ary relation pattern for plant distribution with region and status.
  \item AgentRole pattern for plant uses such as edible, vegetable, and ornamental.
\end{itemize}

\subsection{R2RML Mapping}

The mapping file is \artifact{plant\_management\_r2rml.ttl}. It maps
database rows to ontology individuals. The mapping covers plants, taxonomy,
plant names, synonyms, months, plant distribution, plant parts, colors, and shop
products.

For the full knowledge graph, the course-aligned materialization path is Ontop
over the SQLite database using \artifact{config/ontop.properties}. Ontop CLI
5.4.0 was installed locally and tested with the SQLite JDBC driver. In the
tested environment, Ontop generated SQLite SQL that failed near
\artifact{UNION} for predicates produced by multiple triples maps. Therefore,
the full ABox was materialized with
\artifact{scripts/materialize\_full\_kg.py}, which follows the same normalized
database schema and R2RML predicate structure.

\begin{lstlisting}[language=bash,caption={Materialize the full generated KG.}]
python scripts/materialize_full_kg.py
\end{lstlisting}

The generated artifact is \artifact{data/plantms\_full\_kg.ttl}. It contains
11,104,833 triples, including 416,473 \artifact{plant:Plant} instances and
95 \artifact{plant:ShopProduct} instances. The file was parsed successfully
with an rdflib streaming N-Triples parser. It is intended for import into a GraphDB repository
named \artifact{plantms}.

\section{Step 4: Ontology Alignment}

The selected external ontology is the Plant Ontology (PO). PO was selected
because it describes plant anatomy, morphology, and development. This fits the
local ontology better than broader agriculture vocabularies.

\begin{table}[h]
\centering

\toprule
Candidate & Fit & Reason \\
\midrule
Plant Ontology & Best & Direct match for plant structures \\
Plant Trait Ontology & Good & Useful for traits, but less direct for classes \\
AGROVOC & Medium & Broad agriculture thesaurus \\
Crop Ontology & Medium-low & More focused on crop breeding variables \\
ENVO & Medium-low & Useful for environment, not plant parts \\
NCBI Taxonomy & Low & Needs taxon ids that are not in the data \\
\bottomrule
\end{tabular}
\caption{Checked ontology candidates for Task 4.}
\end{table}

The first alignment artifact is
\artifact{plant\_management\_po\_alignment.ttl}. The mappings are
manual and conservative. Exact mappings are used only for concepts with the same
meaning, such as flower, fruit, and root. Foliage is only a close match to PO
leaf because the concepts are related but not exactly equal.

This first alignment file documents the intended mappings. If the course
requires a tool-generated Alignment API file, this manual mapping can be used as
the baseline for that later run.

\section{Step 5: KG-Based RAG Application}

The RAG application answers natural-language plant questions from the GraphDB
knowledge graph using the SPARQL-generation route from lecture 4. This is
Approach \#1: the RDF graph remains in GraphDB and no vector index is created.

\subsection{Architecture}

The default pipeline has one retrieval path:

\begin{enumerate}
  \item \textbf{Ontology retrieval} -- the CLI searches ontology class and
    property labels for terms relevant to the natural-language question.
  \item \textbf{Entity linking} -- the CLI searches labeled KG entities for
    lexical matches, such as the family \artifact{Araceae}.
  \item \textbf{SPARQL generation} -- the configured LLM provider receives the
    question, retrieved schema terms, linked entities, and a few SPARQL
    examples. It returns a SPARQL \artifact{SELECT} query.
  \item \textbf{Query validation} -- the CLI rejects update operations and remote
    \artifact{SERVICE} calls and limits the maximum number of result rows.
  \item \textbf{SPARQL retrieval} -- the generated query is executed against the
    GraphDB SPARQL endpoint \artifact{http://localhost:7200/repositories/plantms}.
  \item \textbf{Grounded answer generation} -- the configured LLM receives only
    the question, executed query, and returned rows and produces a short factual
    answer.
\end{enumerate}

There is no vector index, embedding model, vector fallback, local KG mode, or
fixed-template mode. The CLI supports a local Ollama provider and an OpenAI Responses API provider.
For OpenAI, the API key is stored locally in an ignored \artifact{.env} file
loaded automatically by the CLI; the checked-in template is
\artifact{.env.example}. The
default OpenAI model is \artifact{gpt-5-mini}.

\subsection{Query Interface}

The CLI supports three modes:
\begin{enumerate}
\item \textbf{Interactive session}
\\python3 scripts/rag\_query.py

\item \textbf{Single query}
\\python3 scripts/rag\_query.py --query "What is the total stock of all Araceae plants in the shop?"

\item \textbf{Inspect retrieved terms and generated SPARQL}
\\python3 scripts/rag\_query.py --show-plan --query "What is the total stock of all Araceae plants in the shop?"

\item \textbf{Use OpenAI Responses API}
\\python3 scripts/rag\_query.py --provider openai --query "What is the total stock of all Araceae plants in the shop?"

\item \textbf{Run the dynamic GraphDB/SPARQL demo questions automatically}
\\python3 scripts/rag\_query.py --demo

\end{enumerate}
